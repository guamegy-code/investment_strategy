# 전략 알림 누락 경로와 복구 설계

검토일: 2026-11-03. 기준 코드: `56c19d5`.
상태: **홈페이지와 Worker 1차 구현·배포 완료. Apps Script는 로컬 수정 완료, 운영 편집기 반영 대기**. 아래 설계 중 아직 적용되지 않은 항목은 현재 적용 범위에서 구분한다.

2026-11-04 후속 반영: 합성 점수의 이력 길이 불일치를 공통 월별 점수와 자동 상태 복구로 보완했다. 최신 배포는 Pages `6cb22a6a`, Worker `dcf4f845-c838-4d56-a0c2-d0350d36e1e1`이며 Node 146개·Python 40개 통과(2개 건너뜀). 아래 1차 구현 시점의 배포·검증 수치는 당시 기록이다. 계산 기준, 보유량 보존과 미발송 사건 이전은 [합성 밸류에이션 계산 일치와 상태 복구](composite-valuation-consistency.md)를 따른다.

현재 알림은 데이터 갱신 실패를 정상 실행으로 처리할 수 있으며, 생성된 신호도 전송 실패 뒤 소실될 수 있다. 가격 조회 복구, 미발송 사건 보존, 장애 통지, 독립 감시를 함께 적용해야 한다. 복구 작업의 진행 상황과 다음 실행을 영속 관리하고, 오류 통지 후에도 미완료 작업을 자동으로 이어 처리하는 것이 기본 동작이다.

검증: Worker·Apps Script Node 검사 79개, 홈페이지 Node 검사 7개, Python 검사 35개 중 33개 통과·2개 건너뜀. 로컬 실제 Durable Object에서 상태 저장·충돌·전송권·ACK·복구 실패 후 재예약도 확인했다. 로컬 런타임은 설치된 workerd 지원 날짜에 맞춘 별도 시험 설정을 사용했고 운영 호환 날짜는 유지했다. 공개 가격 API는 QQQ·SPY·BIL의 11/2, TDF ETF의 11/3 자료를 반환하고, 인증 없는 평가 요청은 401로 차단했다. 화면을 직접 조작하는 최종 검증은 컴퓨터 사용 도구 중단으로 수행하지 못했다.

이메일 보조 안내는 이번 적용에서 제외한다. Telegram 자체를 사용할 수 없으면 미발송과 오류 기록을 유지하며 재시도한다. 전체 Cloudflare 장애에 대한 외부 감시 서비스, 임의 상태 손상에서의 완전 재생, 미국·KRX 달력의 전면 통합, 합성 점수의 이력 길이 동등성·TDF 연결 방식 검증은 후속 항목이다. 새 Apps Script는 향후 KRX 거래일 다섯 번의 복구 일정을 등록하며, 그 범위를 넘긴 장기 실행 중단에 대한 달력은 추가 보완이 필요하다. 기본 홈페이지 초기화나 전략 고점 상태 초기화를 복구 수단으로 사용하지 않는다.

운영 Apps Script에 새 `Code.gs`를 저장하면 기존 트리거가 새 코드를 사용한다. 기존 전략은 `initializeNotificationStates()`를 다시 실행하지 않는다. 백그라운드 발송에 필요한 봇 토큰·채팅 ID는 인증된 평가 요청으로 해당 사용자의 비공개 Durable Object에 등록되며, 공개 API 응답이나 홈페이지에 노출하지 않는다. 개인 YAML은 백그라운드 작업에 저장하지 않아 그 전략의 재평가는 Apps Script 실행이 필요하다.

## 확인 범위와 근거 수준

- 같은 날 앞선 운영 점검: 31P의 평가 기준일은 10월 28일에 정체됐고, 11월 3일 오전 실행은 `SUCCESS`, 발송 0건이었다. 갱신 메타데이터에서 공급자 요청 실패와 Worker 요청 한도 초과가 확인됐다. 공개 가격 조회 경로는 최신 자료를 반환했다.
- 코드 확인: Worker, 전략 실행기, 합성 밸류에이션, Apps Script, 배포 설정, 알림 관련 테스트와 CI를 확인했다. 실제 Apps Script 편집기의 현재 원문을 이번 검토에서 다시 추출하지는 않았다.
- 로컬 장애 주입: 운영 소스를 수정하지 않고 가짜 HTTP·KV·Telegram 응답으로 실패 경로를 재현했다. 실제 알림 전송, 운영 상태 변경, 초기화는 수행하지 않았다.
- 기존 관련 테스트 52개는 모두 통과한다. 이 결과는 정상 기능의 회귀 확인이며, 아래 장애 방어가 갖춰졌다는 뜻은 아니다.
- 아래의 ‘재현’은 로컬 실험 결과, ‘관찰’은 운영에서 확인한 현상, ‘코드’는 실행 순서상 가능한 실패, ‘추가 검증’은 영향이나 운영 설정 확인이 남은 항목이다. 모든 외부 장애와 실제 수신을 완전히 보장할 수는 없다.

## 권고 처리 흐름

1. 구독과 버전을 확인하고 필요한 시장 자료만 조회한다. 요청별 예산·시간 제한·최근 실패 원인을 관리한다.
2. 전략별 필수 자료의 최신성·품질·준비 기간을 검사한다. 실패한 전략은 상태를 전진시키지 않고 `BLOCKED`로 반환한다. 정상 전략은 계속 평가한다.
3. 마지막 확정 상태에서 거래일 순서대로 계산한다. 새 상태와 생성 사건을 하나의 트랜잭션으로 저장한다. 트랜잭션 전후 실행 중단에도 사건이 남아 있어야 한다.
4. 미발송 보관함에서 사건을 가져와 Telegram으로 보낸다. 성공 응답의 message_id를 기록하고 수신자별 ACK를 남긴다. ACK가 유실돼도 다시 처리 가능해야 한다.
5. 재시도 대상은 전송 때까지 보존한다. 반복 일시 오류는 `RETRY_WAIT`를 유지하며 간격을 늘리고 보조 채널로 알린다. 권한·설정 수정이 필요한 경우에만 `WAITING_CONFIG`로 전환한다. 사용자 안내·심각도 상승은 복구 작업을 종료시키지 않는다.
6. 시트의 마지막 평가일·마지막 전달일·장애 상태를 별도로 표시한다. 시트 갱신 실패로 평가나 이미 확인된 전송 결과를 취소하지 않는다.
7. 별도 감시기가 실행 시작 heartbeat, 필수 자료 평가 완료, 중요한 사건 전달 완료를 각각 점검한다. 예약이 사라진 미완료 작업을 다시 예약하고, 만료된 실행권을 안전하게 회수한다. 단순 API 200이나 트리거 실행만으로 정상 판정하지 않는다.

미발송 보관함에는 최소한 `event_id`, 전략 ID/버전/정의 해시, 신호 기준일, 발생 시각, 원본 내용, 수신자 ID, 전송 상태, 시도 횟수, 다음 시도 시각, 마지막 오류, message_id, ACK 시각을 남긴다. 전달 상태는 `PENDING → DELIVERED`, 실패 시 `RETRY_WAIT` 또는 `WAITING_CONFIG`로 구분한다. 장애의 `NEEDS_ATTENTION` 표시는 별도 필드로 둬 자동 복구와 병행한다. 사용자 확인은 별도 `USER_ACK`다.

## 자동 복구 실행 계약

### 진행 저장과 재개

- 작업을 `자료 수집 → 유효성 확인 → 순차 평가 → 사건 저장 → 전달` 단계로 나누고 각 단계의 완료를 기록한다. 기준일, 전략 정의·계산 버전, 입력 자료 버전을 고정해 한 작업 안에서 서로 다른 계산 조건이 섞이지 않게 한다.
- 수집 작업은 번호가 아니라 `종목 + 필요 기간 + 자료 종류 + 버전`으로 식별한다. 병렬 실행에서 20번째가 실패하고 21번째가 성공했다면 성공한 21번째도 재사용한다. 성공 HTTP 응답만으로 완료 처리하지 않고 **자료 저장이 확인된 뒤** 체크포인트를 확정한다. 저장 실패·실행 강제 종료 시 확정되지 않은 항목은 다시 조회할 수 있다.
- 결과와 완료 표시를 한 트랜잭션에 저장하거나, 변경하지 않는 결과 버전을 먼저 저장한 뒤 원장에서 그 버전을 참조한다. 원장에는 결과 식별자·검증 상태·시도 횟수·다음 실행 시각·마지막 진전 시각을 둔다. 최신 캐시 키만 참조해 다른 호출의 갱신을 잘못 가져오지 않는다.
- 50회의 끝까지 실행한 뒤 복구를 시도하지 않는다. 남은 외부 요청·시간 예산이 작업의 최대 필요량보다 작으면 미리 중단하고 재개를 예약한다. 목록 조회, 대체 호스트, 재시도, 리다이렉트도 예산에 포함한다. ‘종목 1개’가 외부 요청 1회라는 가정은 금지한다.
- 일시 통신 오류는 같은 호출의 예산 내에서 짧게 재시도할 수 있다. 호출당 한도 소진은 새 실행으로 넘긴다. 동일 작업 크기로 계속 실패하면 배치를 줄인다. 한 항목이 나머지 전략을 계속 막지 않도록 실패 항목을 격리하고 대기 작업을 순환 처리한다.
- 재개 시 결과의 기준일·준비 기간·정합성을 재확인한다. 다음 거래일로 넘어가면 기존 자료는 재사용하면서 필요한 새 구간만 추가한다. 과거 미평가 구간은 상태 재생에 필요한 의존 작업으로 남기고, 이전 날의 진행을 전부 버린 채 최신일을 계속 쫓지 않는다.

| 공급자 통신·429·5xx·공표 지연 | retry_after 또는 상한 있는 backoff와 시간 분산, 검증된 대체 경로, 이후 소량 재조회로 정상 여부 확인 | 검증 가능한 자료를 계속 확보하지 못하는 경우. 장애 안내 후에도 저빈도 재조회 유지 |
| 가격 캐시 손상·이력 축소 | 손상 버전 격리, 정상 원본과 겹치는 구간 검증, 필요한 이력 재수집 후 재계산 | 원본 복원이 불가능하거나 자료 불일치가 해소되지 않음 |
| 전략 상태 손상·누락 | 검증된 마지막 체크포인트와 당시 정의·입력 자료에서 순차 재생, 기존 사건 원장과 대조 후 전환 | 신뢰 가능한 복구 기준 없음. 짧은 최근 이력으로 고점 상태를 새로 초기화하지 않음 |
| Telegram 일시 실패·형식 오류 | 미발송 재전송, 일반 텍스트·길이 분할, 준비된 보조 채널로 전달 | 토큰 폐기·봇 차단·수신 주소 오류 등 설정 변경 필요 |
| 전송 결과·ACK 불명 | 사건 ID 유지, 확인된 message_id 재사용, ACK 재처리. 결과 불명이면 중복 가능성을 표시해 재전송 | 수신자 확인이 필요한 경우에도 새 전략 평가·다른 사건 처리를 멈추지 않음 |
| 시트·로그 쓰기 실패 | 원장을 기준으로 표시 자료를 나중에 재구성, 전송·복구 처리는 계속 진행 | 권한 취소·시트 영구 삭제. 자동 대체 시트 생성이나 잘못된 주소로 전송하지 않음 |
| 실행기 종료·트리거 누락 | 미완료 작업과 만료된 실행권을 감지해 준비된 대기 실행기가 자동 인계 | 대기 경로도 사용할 수 없거나 외부 권한 복구 필요 |
| 일일 호출·쓰기·메일 할당량 소진 | 비필수 작업 축소, 가능한 별도 채널 안내, 해당 자원의 재사용 가능 시점 이후 자동 재개 | 현재 요금·구조로 정상 부하조차 수용하지 못함. 자동 유료 전환은 하지 않음 |
| 정의 불일치·코드 오류·권한 만료 | 검증된 고정 정의·호환 배포본이 준비돼 있으면 해당 경로 사용. 해당 작업 격리, 설정 변경 감지 후 검증·재개 | 호환 복구 경로가 없거나 새 인증·코드 수정이 필요. 임의 전략 변경·무조건 롤백은 하지 않음 |

반복 실패는 `빠른 재시도 → 간격 증가 → 저빈도 정상 여부 확인`으로 전환한다. 최대 연속 시도 횟수는 한 번의 적극적인 복구 구간을 제한하며, 작업을 영구 폐기하는 횟수가 아니다. 데이터 공급이 돌아오거나 설정이 수정되면 원장의 대기 작업이 자동으로 재개돼야 한다. 사용자에게 필요한 조치를 알린 상태와 시스템이 계속 복구 중인 상태를 동시에 표시할 수 있어야 한다.

호출당 한도와 일일 한도는 다르다. 새 호출로 넘어가도 일일 요청·저장소 쓰기 한도는 복원되지 않는다. heartbeat·체크포인트·재시도가 새 장애를 만들지 않도록 자원별 사용량을 추적하고, 변경 없는 메타데이터·로그 쓰기는 합친다. 복구 예약 시각은 각 서비스의 정책을 기준으로 계산한다. [Worker 한도](https://developers.cloudflare.com/workers/platform/limits/), [KV 한도](https://developers.cloudflare.com/kv/platform/limits/)

### 실행 중단 뒤에도 복구 작업이 살아 있는 구조

자료 수집·평가 작업의 실행권에는 소유자, 만료 시각, 증가하는 세대 번호를 둔다. 대기 실행기가 인계하면 늦게 돌아온 이전 실행기의 저장은 세대 번호 검사로 거부한다. 외부 전송의 중복 가능성은 완전히 제거할 수 없으므로 전송 직전 실행권 재확인, 안정된 사건 ID, ACK 원장을 함께 사용한다.

정상 경로는 작업별 재개 예약으로 실행하고, 별도 주기 점검이 `미완료인데 예약 없음`, `실행권 만료`, `오랫동안 진행 없음`을 찾아 다시 실행한다. Durable Object alarm을 쓰더라도 플랫폼 기본 재시도에만 의존하지 않는다. 공식 문서는 자동 재시도 횟수가 유한하다고 명시하므로 애플리케이션의 다음 실행 기록과 예약 복원을 함께 구현한다. [Alarm 재시도](https://developers.cloudflare.com/durable-objects/api/alarms/)

Apps Script가 멈췄을 때 Cloudflare 대기 처리기가 평가·전송까지 인계하려면 구독 구성과 필요한 비밀값이 미리 준비돼 있어야 한다. 개인 YAML은 기존 비저장 정책을 유지하므로, 별도 보관에 합의하지 않은 개인 전략은 외부 실행기가 재평가할 수 없다. 이 경우 이미 저장된 사건 전달과 장애 안내까지만 가능하다. 공개 전략의 구독 구성은 버전·활성 상태·동기화 시각을 가진 복구용 설정으로 준비한다.

`automation_enabled=false`나 명시적 구독 해제는 장애로 간주해 되살리지 않는다. 운영 중단은 트리거 삭제만으로 표현하지 않고 공유된 운용 설정에 기록한다. 대기 실행기는 이 설정을 확인한 작업만 인계한다. Google 권한 철회는 외부 감시기가 복원할 수 없으며, 설치형 트리거도 생성한 계정의 권한으로 실행된다. [설치형 트리거 권한](https://developers.google.com/apps-script/guides/triggers/installable)

Cloudflare 자체가 중단되면 같은 환경의 원장·대기 실행기도 영향을 받는다. Google 또는 독립 외부 감시기는 장애를 알리고 복구 여부를 확인하며, Cloudflare가 돌아오면 작업을 다시 깨운다. 전체 플랫폼 장애 중에도 계산을 계속하려면 별도 플랫폼에 검증된 계산기·상태 복제까지 필요하다. 이는 아직 준비되지 않았으며 감시만으로 가능하다고 보장하지 않는다.

### 복구 완료 판정

자료 수집 완료, 기대 기준일까지 평가 완료, 중요한 사건 전달 완료를 각각 기록한다. 필수 사건의 주 채널 전송이 실패했어도 보조 채널에 전달했다면 `대체 전달 완료·주 채널 복구 중`으로 구분한다. 시트 표시 복구와 선택적인 사용자 확인은 별도 상태로 관리해 다음 평가를 막지 않는다. 새 거래일 작업이 추가됐다는 이유로 이전 장애 원인·미발송 사건·복구 횟수를 초기화하지 않는다.

**장기간 장애 복구 시 과거 주문을 그대로 연속 지시하지 않는다.** 누락 구간은 순차 재계산해 감사 이력으로 보존하고, 현재 유효한 목표와 그동안의 변화, 전달 지연을 함께 안내한다. 이미 대체된 과거 사건은 명시적 `SUPERSEDED` 관계로 남긴다. 중간 방어 신호가 나중에 해제돼도 발생 사실은 복구 보고에 포함한다. 모델의 가상 체결과 실제 계좌 체결은 다르므로, 미수신 기간에 모델이 체결했다고 해서 사용자가 체결한 것으로 표시하지 않는다.

## 홈페이지의 데이터·계산 상태와 재시도

### 관리 범위

홈페이지는 여러 방문자가 여러 전략의 자료·분석 결과를 확인하는 공개 서비스다. 홈페이지의 복구 대상은 전략 정의 로드, 시장 자료 조회, 지표·전략 계산, 차트·표 표시다. Telegram의 개인 구독·발송·미발송 원장과 독립적으로 동작하며, 홈페이지에 개인 알림 관리·재전송·수신 확인 기능을 추가하지 않는다. 이 기능을 위해 개인 계정 연결이나 로그인을 필수로 도입하지 않는다.

`src/web/app.js`의 `fetchProxyTickerData()`(756)는 `/prices`로 자료를 가져오고 `run()`(909)은 브라우저에서 전략을 계산한다. 현재는 조회 실패 시 저장 자료가 있으면 콘솔 경고 후 계속 계산하며, 응답의 자료 최신성 정보를 화면 상태로 연결하지 않는다. 조회를 시도한 시각과 실제 자료 기준일을 구분해 표시해야 한다. `resetUserState()`(979)는 가져온 전략·선택 상태·브라우저 캐시를 지우므로 재시도 버튼으로 사용하지 않는다.

### 화면에 표시할 상태

| 대상 | 표시할 정보 | 실패·지연 시 표시 |
|---|---|---|
| 전략 정의 | 선택한 전략의 정의 버전, 로드 완료 여부 | 해당 전략 로드 실패와 다시 불러오기 |
| 종목별 시장 자료 | 기대 거래일, 실제 최신 확정 자료일, 마지막 조회 시각, 필요한 이력의 확보 여부 | 예: QQQ 자료 지연, 마지막 자료 10/29. 저장 자료 사용 여부와 재시도 가능 시각 |
| 전략별 계산 | 계산 중·완료·자료 대기·계산 실패, 계산에 사용한 자료 기준일·정의 버전 | 실패한 전략만 표시하고 정상 계산된 다른 전략은 계속 조회 가능 |
| 차트·표 | 계산 결과의 기준일과 표시 완료 여부 | 이전 결과를 남길 때 ‘이전 계산 결과’ 표시. 최신 자료를 받았어도 재계산 전에는 최신 결과로 표시하지 않음 |
| 전체 선택 항목 | 준비된 자료 수, 완료된 전략 수, 실패·지연 항목 수 | 실패 원인의 짧은 설명과 해당 항목의 재시도 동작 |

HTTP 200이나 캐시가 존재한다는 사실만으로 최신 상태를 판정하지 않는다. `/prices`의 종목별 freshness 정보, 실제 자료 범위, 필수 지표 준비 기간, 계산 결과의 입력 자료 버전을 함께 확인한다. 과거 기간을 지정한 분석은 요청한 기간에 필요한 자료 충족 여부로 판단하며, 최신 자료일까지 요청한 화면에만 최신 거래일 충족 여부를 적용한다. 갱신 시도는 실패했어도 유효한 확정 자료가 이미 있으면 자료 상태와 최근 조회 오류를 별도로 표시한다.

### 사용자 재시도

| 동작 | 처리 내용 | 보존 범위 |
|---|---|---|
| 데이터 다시 받기 | 선택 전략에 필요한 종목 중 지연·누락·실패한 자료를 다시 조회하고 준비되면 영향받는 전략 재계산 | 확보한 정상 자료와 다른 전략의 결과 유지. 성공 자료는 필요한 새 구간만 추가 |
| 전략 다시 계산 | 해당 전략의 정의·입력 자료를 검증한 뒤 그 전략의 결과 캐시만 우회해 계산 | 종목 자료·가져온 YAML·화면 선택 유지. 필수 자료 부족 시 먼저 자료 재시도로 연결 |
| 실패 항목 다시 시도 | 선택한 화면의 정의 로드·자료 조회·계산·표시 실패를 의존 순서대로 복구 | 완료된 단계 재사용. 공통 종목은 한 번 조회하고 관련 전략에 함께 반영 |

재시도 중에는 진행 상태를 보여주고 같은 작업의 연속 클릭을 합친다. 자동 복구가 진행 중이면 별도 작업을 만들지 않고 그 진행을 보여준다. 브라우저의 일시적인 조회 생략·실패 결과 캐시는 대상 항목에 한해 우회할 수 있지만, 공급자 retry_after와 서버의 요청 예산·쿨다운은 준수한다. 재시도를 위해 전체 사용자 데이터나 캐시를 초기화하지 않는다.

자료 조회는 화면이 열린 동안 제한된 횟수·간격으로 자동 재시도하며, 오류와 다음 시도 시각을 화면에 표시한다. 일시적인 계산 작업 중단은 작업자를 재생성하거나 기존 대체 실행 경로로 재개하고, 동일 입력에서 반복되는 계산 오류는 계속 실행해 화면을 멈추게 하지 않는다. 화면 표시만 실패했으면 유효한 계산 결과로 다시 그린다.

### 공통 자료와 사용자별 계산의 경계

- 종목별 시장 자료는 서버의 공개 가격 캐시를 재사용할 수 있다. 여러 방문자가 같은 종목·범위를 동시에 재시도해도 서버에서 가능한 범위 내에 중복 조회를 합치고, 캐시 갱신·외부 요청 횟수를 제한한다. 공개 재시도로 다른 방문자의 자료를 삭제하거나 모든 전략의 전체 이력을 다시 받게 하지 않는다.
- 선택 전략·분석 기간·가져온 YAML·계산 결과는 기존 브라우저 중심 구조를 유지한다. 계산 재시도가 다른 방문자의 화면이나 Telegram 전략 상태를 변경하지 않는다. 개인이 가져온 YAML은 별도 동의 없이 서버 공유 작업에 넣지 않는다.
- 기존 `/prices` 응답의 최신성 정보를 우선 활용한다. 별도 공개 자료 상태 조회·갱신 요청 API가 필요하면 시장 자료에만 한정하고 허용 종목·범위·요청 빈도·공유 작업 예산을 검증한다. 운영용 키나 Telegram 비밀값은 브라우저로 전달하지 않는다.
- 서버가 접수한 공통 자료 수집 작업을 영속화하는 경우에는 브라우저 종료 후에도 이어 처리할 수 있다. 브라우저 계산은 종료 시 멈출 수 있으며, 다시 접속하면 저장된 자료·완료 결과를 확인해 미완료 부분을 재개한다. 현재 구조에서 모든 웹 계산이 창을 닫은 뒤에도 실행된다고 보장하지 않는다.
- 홈페이지가 사용하는 공통 자료와 계산 엔진의 정합성은 개인 알림 경로와 함께 검증하되, 서로의 실행 상태를 소비하지 않는다. 분석 시작일·초기 상태·계산 버전이 다르면 공개 분석과 개인 알림 결과가 달라질 수 있으므로 비교 시 기준을 함께 표시한다.

Telegram이 중단돼도 홈페이지는 자체 자료와 계산 결과를 조회·복구할 수 있어야 한다. Cloudflare 가격 API까지 중단됐다면 홈페이지에 마지막 자료일과 연결 오류를 표시하고 재시도를 제공한다. 자료를 확보하기 전에는 최신 판단이 완료됐다고 표시하지 않는다.

### 기본 전략 수와 요청량

- 홈페이지는 목록 JSON과 활성 전략 번들 JSON을 읽는다. 번들을 사용하는 현재 경로에서 전략 정의 로드 요청은 기본적으로 두 번이며, 전략 수 증가는 주로 전송 크기를 늘린다. 번들을 사용하지 않는 대체 경로에서는 개별 YAML 요청이 늘어난다.
- 가격 조회는 실제 분석하는 전략의 종목·조회 구간과 캐시 상태에 따라 결정된다. 공통 종목과 범위는 재사용할 수 있으므로 전략 수와 요청 수가 비례하지 않는다. 새 종목·다른 필요 이력 구간이 추가되면 요청과 데이터량이 늘 수 있고, 전략별 계산량은 증가한다. 초기 방문은 첫 활성 전략만 선택하는 현재 동작도 고려한다.
- 중앙 숨김은 화면에서 선택할 전략과 활성 번들의 크기를 줄인다. 다른 노출 전략의 source인 정의는 계산에 필요하므로 번들에 보존한다. 현재 알림 Worker의 `loadDefinitions()`는 전체 목록을 읽으므로 숨김만으로 그 경로의 49회 요청을 줄이지 못한다.
- 2026-11-03 노출 조정: 19·21·25·25P·26P·27·27P·28·28P·29P를 중앙 숨김 목록에 등록해 노출 전략을 24개에서 14개로 줄였다. Pages `031c9cc2`와 공개 주소에서 확인했다. YAML 매매 규칙과 개인 알림의 전략 식별자는 유지한다. 브라우저의 저장된 가져오기 기록으로 숨김이 풀리는 경로도 수정했다.


## 오류 통지와 복구 정책 제안

다음 시간은 KST 기준 제안값이며 실제 트리거 지연과 개장 일정에 맞춰 검증해야 한다. 장애 메시지는 정기 요약 설정(`weekly`, `none`)과 별도로 동작한다.

| 상황 | 사용자 안내 | 복구·재시도 |
|---|---|---|
| 첫 평가에서 필수 데이터 지연·평가 실패 | 해당 전략의 평가가 완료되지 않았음을 즉시 1회 안내. ‘신호 없음’으로 표현하지 않음. | 예산 내 재조회, 검증된 캐시·대체 경로 확인. 오류 종류별 backoff. |
| 호출당 요청 한도 초과 | 작업을 분할해 이어 처리 중임을 안내. | 확정 결과 보존, 배치 축소, 새 실행 예약. 사용자 개입 없이 완료를 목표로 함. |
| seed 누락·상태 손상 | 자동 복원 중인 전략과 평가 지연을 안내. | 검증된 체크포인트에서 복원·순차 재생. 안전한 복원이 불가능할 때만 개입 요청. |
| 인증·권한·설정 오류 | 필요한 조치와 영향 범위를 즉시 안내. | 작업 보존, 설정 변경 후 재검증·자동 재개. 복구 불가능한 인증 요청의 반복은 제한. |
| 08:15까지 유효한 평가 결과 없음 | 독립 감시기가 실행 중단 또는 평가 미완료를 감지해 안내. | 누락 예약 복원·만료된 실행권 인계. heartbeat와 평가 완료 조건을 구분. 휴장일에는 검증된 일정으로 면제. |
| 08:40까지 미복구 또는 중요 사건 미전달 | 개장 전 안내 실패 가능성을 강조하고 사전 등록 이메일에도 통지. | 08:50까지 최신 상태·미발송 목록 재확인. 예약 시각보다 실제 실행이 늦을 가능성을 감시 허용시간에 반영. |
| Telegram 429·통신 오류·5xx | 전송 대기 상태 유지. 반복되거나 개장 전 전달 마감이 가까우면 이메일 안내. | retry_after 우선, 재시도 예약. 한 실행에서 오래 잠들어 기다리지 않음. |
| Telegram 토큰 오류·봇 차단·채팅 오류 | Telegram 대신 이메일로 즉시 안내. | 설정 수정 전까지 사건 보존. 동일 장애 안내는 제한된 간격으로 재통지. |
| 09:00 이후 복구 | ‘지연 복구’와 원래 신호일·현재 목표를 함께 안내. 이미 지난 개장 시가에 실행 가능한 것처럼 쓰지 않음. | 장중 복구 평가와 미발송 전송을 계속 수행. 장 종료 후에는 다음 실행 가능 시점을 구분. |
| 장애 해소 | 최신 필수 자료로 평가와 중요한 미발송 처리를 완료한 뒤 복구 안내 1회. | 성공 HTTP 한 번으로 장애를 닫지 않음. 보조 채널 전달·주 채널 장애·사용자 미확인은 별도 표시. |

오류 안내는 `영향 전략 + 오류 종류 + 기대 기준일 + 마지막 정상 기준일 + 자동 재시도 상태 + 필요한 행동`을 짧게 전달한다. 예:

> [전략 알림 점검 필요] 31P의 최신 평가를 완료하지 못했습니다. 필요한 미국장 기준일은 11월 2일, 마지막 정상 평가일은 10월 28일입니다. 가격 갱신 오류로 자동 복구를 시도 중입니다. 현재 무알림은 리밸런싱이 없다는 뜻이 아닙니다.

같은 장애는 전략·원인·발생 구간으로 묶어 첫 발생, 심각도 상승, 장기 지속, 복구 때 통지하고 영향받는 기대 거래일을 갱신한다. 날짜가 바뀌어도 지속 중인 장애를 새 장애로 반복 생성하지 않는다. 기본 재통지는 30분 간격으로 제한하되 새 리밸런싱 사건과 별개로 관리한다. 장애 통지 실패도 전송 보관함과 감시 대상에 포함하며 재귀적으로 오류 메시지를 생성하지 않는다. 메시지에는 자동 복구 중인지, 다음 재시도 시각이 언제인지, 사용자 조치가 필요한지를 구분해 표시한다. 안내 발송 성공·실패는 복구 작업의 진행 조건으로 사용하지 않는다.

## 보조 채널과 독립 감시의 구성

- **일반 실패:** Apps Script가 살아 있고 Telegram도 사용 가능하면 즉시 장애 메시지를 보낸다.
- **Telegram만 실패:** Apps Script의 MailApp으로 사전 등록한 사용자 이메일에 장애와 미전달 사건 ID를 보낸다. 수신 주소 설정과 메일 권한 승인이 필요하고 일일 메일 잔여 한도를 검사한다. 주소는 추측하지 않는다.
- **Apps Script 실행 중단:** 별도 Cloudflare 감시 작업이 성공 heartbeat와 완료 상태를 확인하고 재개 예약을 복원한다. 복구 구성·비밀값이 준비된 공개 전략은 대기 처리기가 인계한다. 감시 자체는 가격 전체 조회를 하지 않고, 실제 복구 작업을 별도 예산으로 실행한다.
- **Cloudflare 또는 Google 중단, Telegram 동시 장애:** 둘과 독립된 외부 heartbeat 감시 서비스의 이메일 통지를 둔다. 같은 Apps Script에 두 번째 트리거만 만드는 것으로는 이 범위를 방어할 수 없다. 외부 서비스 선택과 수신 주소·연결 설정은 도입 시 확정한다.
- **중요 알림 사용자 확인:** 전송 성공과 사용자 확인을 분리하고, 미확인 상태가 지속될 때 보조 채널로 재안내하는 기능을 권고한다. 두 채널 모두 실패하면 저장된 사건을 유지하고 복구 후 안내한다.

Google의 기본 트리거 실패 이메일은 보조 수단이다. 현재처럼 성공으로 끝나는 stale 실행이나 삭제된 트리거까지 감시하지 못한다. Apps Script의 실행 시간·총 트리거 시간·메일 한도도 별도 고려해야 한다. [설치형 트리거](https://developers.google.com/apps-script/guides/triggers/installable), [할당량](https://developers.google.com/apps-script/guides/services/quotas), [MailApp](https://developers.google.com/apps-script/reference/mail/mail-app)

Telegram의 길이 한도는 entity 처리 후 4,096자이며, 응답의 `retry_after`를 재시도에 사용할 수 있다. 요청 성공과 사용자의 확인은 별개로 취급한다. [sendMessage](https://core.telegram.org/bots/api#sendmessage), [ResponseParameters](https://core.telegram.org/bots/api#responseparameters)

## 적용 순서와 완료 기준

1. **현재 누락 복구 준비:** 현재 snapshot·전달 이력 보존, 최신 자료와 저장 상태로 31P 누락 구간 재계산. 초기화로 고점 상태를 지우지 않는다. 복구 안내는 현재 목표와 지연 사실을 포함하도록 준비한다.
2. **당일 위험 차단:** 전체 YAML 조회 제거, 자료 최신성·평가 완료 검사, 장애 통지, 시간 창 이후 복구 처리. 가격 이력 축소와 backoff 오류 정보 소실을 함께 수정한다.
3. **자동 재개와 전달 내구성 확보:** 영속 작업 원장·종목별 체크포인트·한도 전 중단과 새 실행 예약, 상태·사건 원자적 저장, 미발송 보관함, 수신자별 ACK, 재시도·장애 이메일. 수집 도중부터 수신자 ACK까지 모든 중단 지점에 대해 재개 검증을 통과시킨다. 한도 초과·일시 전송 실패 뒤 사용자가 수동 실행하지 않아도 완료돼야 한다.
4. **독립 감시와 대기 실행 도입:** 예약 누락 복원, 만료 실행권 인계, 명시적 일시정지 준수, 외부 이메일 fallback, 구독·전략 버전과 배포본 확인. 대기 경로가 실제 사용할 설정·권한·비밀값을 사전 준비한다.
5. **계산·일정 검증 확대:** 시장별 날짜 정렬, 휴장·지표 준비 기간·FRED 공표일·TDF 연결·이력 길이 동등성 점검. 알림 보완을 이유로 31번 전략의 매매 규칙을 바꾸지 않는다.
6. **공개 홈페이지 복구:** 자료별 최신성·확보 범위와 전략별 계산 상태 표시, 실패 자료 재조회·해당 전략 재계산·표시 재시도 제공. 공통 가격 자료는 재사용하고, 개인 알림 상태와 독립적으로 검증한다.

배포 전에 다음 실패 주입 검사를 통과해야 한다.

- 전체 목록 증가, Yahoo 두 호스트 실패, 429·타임아웃·FRED 지연에도 요청 예산 준수 및 영향 전략 오류 통지.
- 오래된 데이터·누락 거래일·필수 지표 NaN·과거 관측치 반복에서 정상 `NO_SIGNAL` 금지.
- 상태 저장 직전/직후, 응답 유실, Telegram 실패, 전송 성공 후 ACK 실패, 시트 쓰기 실패, 부분 배치 실패에서 사건 보존 및 재전송.
- 중복 실행·다중 수신자에서 상태 역행 방지, 각 수신자의 독립 전달, 이미 ACK된 사건의 정상 중복 억제.
- 미발송이 남은 09:00 경과·연휴·주말·장기 장애 후 복구에서 적절한 지연 안내와 현재 목표 제시.
- 트리거 삭제·락 연속 실패·권한 만료·Worker 중단 때 독립 감시가 경보. Telegram 차단 때 실제 등록 이메일 경로 검증.
- 긴 사건·HTML 오류·응답 JSON 오류를 처리하고, 로그와 오류 안내에 비밀값이 없을 것.
- 평가액 조회 전후 계산 이력 보존, 전체 이력 대비 증분 상태·목표·알림 동등성, 31·31P 원본 규칙 보존.
- 50개 논리 작업 중 20번째 실패 시 확정된 1~19번째 결과 재사용, 병렬로 성공한 이후 작업도 재사용. 작업별 외부 요청 수가 달라도 한도 준수. 저장 직전 강제 종료된 작업은 누락 없이 재실행.
- 작업 예약 저장 전후 중단, 기본 alarm 재시도 소진, 실행권 만료에서 별도 점검이 자동 재개. 오래된 실행기의 늦은 쓰기 거부. 수동 실행 없이 최종 완료할 것.
- 다음 거래일 전환·긴 연휴에도 이미 확보한 자료를 재사용하고 날짜·버전이 섞인 평가 방지. 실패 종목 때문에 다른 전략이 계속 대기하지 않을 것.
- 일일 저장소·메일 할당량 소진 시 빠른 재시도 폭주 방지, 사용 가능 시점 이후 자동 재개. 사용자 오류 안내 실패가 복구 처리를 막지 않을 것.
- 주 실행기를 중단한 상태에서 준비된 대기 실행기의 실제 평가·전달 인계 검증. 사용자 일시정지 시 자동 인계 금지. 토큰 수정 후 대기 사건 자동 재개 및 복구 안내 검증.
- Telegram 중단과 무관하게 홈페이지의 자료 조회·전략 계산 가능. 오래된 자료를 HTTP 200으로 반환해도 지연 표시, 종목 하나의 실패 시 영향받는 전략만 자료 대기로 표시. 과거 분석 기간의 자료 충족 여부도 정확히 판정.
- 홈페이지 재시도 시 정상 자료·다른 전략 결과·가져온 YAML·선택 상태 보존. 자료 갱신 후 영향받는 전략만 재계산하고 이전 결과와 새 자료 기준일 혼용 방지. 계산·표시 실패를 각각 복구.
- 여러 방문자·탭의 동시 재시도에서 공통 자료 중복 요청 제한, 공급자 대기 시간 준수. 브라우저 재접속 후 미완료 계산 재개. 홈페이지 작업이 개인 구독·고점 상태·발송 이력을 변경하지 않고 개인 정보나 운영 키를 조회하지 않을 것.

검증된 실패 주입 시나리오는 일회성 수동 점검으로 끝내지 않고 CI에 포함한다. 현재 GitHub의 `Notification security` 작업은 Python 보안 테스트만 실행하며 Worker·Apps Script 장애 복구 검사를 수행하지 않는다.
